## 一、那个项目是什么

- **引擎**：Crazy Storm（LuaSTG 系的国产引擎），脚本语言是 `[时间]命令(...)` 形式，
  和 LuaSTG 的概念基本能对上（`SetEnemy`/`AddEvent`/`For..To..Step`）。
- **资源格式**：`Content/` 下都是 TripleDES-ECB-PKCS7 加密的，key 在
  `docs/part-ii-differences-and-restore-plan.md` §3（4 组，Part II / III 相同）。
  - `Content/Data/*.xna` → **type 2** → 文本脚本 / BinaryFormatter
  - `Content/Data/*.dat` → **type 0** → PNG 图集
  - 16 字节 key 要按 `K1|K2|K1` 补成 24 字节再喂给 3DES。
- 解密命令（本机 LibreSSL 认 `des-ede3`，不认 `des-ede3-ecb`）：
  ```bash
  openssl enc -des-ede3 -d -K <24字节hex key> -in X.dat -out X.png
  ```

## 二、怎么定位到「哪张卡是哪个文件」

数据文件的命名是一套**编号体系**，靠三个东西串起来：

1. `Content/Data/<关卡><0><难度>.xna` = **关卡脚本**
   - 第 1 位 = 关卡号（1–6），第 3 位 = 难度（**1=Easy 2=Normal 3=Hard 4=Lunatic**）
   - 例：`604.xna` = **Stage 6 Lunatic**
2. 关卡脚本里的 `SetBossCard(是否符卡, 卡号后缀, ..., 血量, ...)`
   → 对应的弹幕数据是 **`b<关卡号><卡号后缀>.xna`**（例：`SetBossCard(1,60,...)` → `b660`）
3. `Content/Data/s<难度>.xna` = **符卡练习列表**（UTF-16LE），
   每行 `<卡id> <卡名>`，`f` 前缀的是非符。按 `SetBossCard` 的出现顺序一一对应，
   所以**卡名是这么对到 b 文件上的**。

已验证的对应关系（第 6 关）：

```
601 ↔ s1 (Easy)     602 ↔ s2 (Normal)
603 ↔ s3 (Hard)     604 ↔ s4 (Lunatic)
```

## 八、坐标与角度的换算（翻 LuaSTG 时必须先做）

```

lua_angle = −cs_angle       (CS 0°=右 90°=下；LuaSTG 0°=右 90°=上)
```

⚠ 不翻 y 的话，整张卡会**上下镜像**；不翻角度的话方向全错。

## 十二、★ 绑定关系（我第一版完全搞错的地方）

**批次不是各自独立的发射器，它们是一棵「挂载树」。**

| 字段 | 含义 |
|---|---|
| `bindid = -1` | **根**：自己造子弹（`Batch.cs:1621`） |
| `bindid = N` | **炮塔**：挂在「第 N 个批次造出来的子弹」身上，**自己不造子弹**（`Batch.cs:1703`） |
| `Bindwithspeedd` | 挂上去时 `fdirection += 运载弹的 fdirection`（炮口朝向跟着运载体的航向转） |
| `Deepbind` | 每个运载弹上**克隆一份**炮塔（位置每帧被运载弹覆盖，`Batch.cs:1711-1714`），而不是只吐一发 |
| `parentid` | 是**层号**（`LayerArray[parentid]`），不是父批次 |

也就是说：一颗「子弹」可以是**运载体**，炮塔骑在它身上，它飞到哪炮塔就在哪发弹。
图案是靠「载体 + 挂在上面的炮塔」搭出来的，不是靠一堆固定坐标的发射器。

### 批次的完整语义（读 `Batch.cs:372-403` 与 `Shoot()` 得到）

**一个批次 = 一个会动的物体**，不是「一个发射器配置」：

| 概念 | 说明 | 出处 |
|---|---|---|
| `begin` / `life` | 它在**全局时间**里的激活窗口：`Times.now ∈ [begin, begin+life-1]`，之外整段 `return` | `:390` |
| `time` | 它自己的帧计数 `= Times.now − begin + 1` | `:396` |
| 位置 | 每帧 `speedx += aspeedx; x += speedx; fx += speedx`（y 同）——**它自己在移动**，`fx/fy` 跟着走 | `:400-405` |
| 发射 | 每 `t` 帧调一次 `Shoot()`（`Deepbind` 时每帧调） | `:1545-1551` |

**`Shoot()` 分两种情况**（`:1621`）：

```
bindid == -1  →  造 tiao 发「运载弹」（自己就是根）
bindid == N   →  找到第 N 个批次造出的、还活着的运载弹，
                 对**每一颗**都从它身上吐 tiao 发子弹出膛（自己不独立造弹）
```

所以**图案是靠「载体 + 骑在它上面的炮塔」搭出来的**：
载体飞到哪，炮塔就从哪发弹。这就是我第一版完全没做的东西。

`Bindwithspeedd`：挂上去时 `barrage2.bindspeedd = 运载弹.speedd`（炮口朝向跟载体航向走）。
`Deepbind`：每个运载弹上**克隆一份**炮塔，位置每帧被运载弹覆盖（`:1711-1714`）。

### ✅ 对上了：时间会循环 + 子弹有寿命

之前 `life=13 / sonlife=1` 看起来太稀，是因为我漏了两条：

**① `Times.now` 会循环**（`Time.cs:1904-1907`）
```csharp
now++;
if (now > total && ...) { now = 1; times++; ... }   // ← 绕回 1，整套图案重来
```
循环时**只重置批次**（`item2.copys = item2.Copy()`、清事件、重算 fx/fy），
**不清场上的 Barrage** —— 已经飞出去的弹跨循环保留。
（`Layer.ReturnComponentsToPool()` 只回收 Batch/Lase/Cover，不含 Barrages。）

**② 子弹到期会删**（`Barrage.cs:1530-1545`）
```csharp
if (time > add + life) {                 // life = sonlife；add = Mist ? 15 : 0
    if (Dispel & type >= 0) { fadeout += 5; alpha = 100-fadeout; ...
        if (fadeout >= 100) NeedDelete = true; }    // 淡出 20 帧再删
    else { /* 直接删 */ }
}
```

**⚠ 第 ② 条漏了会出大问题**：运载弹 `sonlife=1`，不删的话它会**永远赖在场上**，
炮塔就一直挂在它身上发弹 —— 数量指数级涨。我的第一版实测
1800/3600/7200 帧 = 5270 → 11795 → 26036（无限涨）；补上到期删除后
三个时长**都是 286**（稳态）。

## 十三、第二次修正：四张属性表、分图层绑定、子事件组、坐标

上面第十二节那一版**还是错的**。实机打出来只有顶上的花、缩放不对、竖向枝条没有小花、
开卡还多出原版没有的散射弹。逐条查源代码后，找到四个真正的语义：

### ① `bindid` 只在**本图层**里找（这是「只有顶上的花」的根因）

`Batch.cs:1703`：

```csharp
for (int k = 0; k < layerm.LayerArray[parentid].Barrages.Count; k++)
    if (Barrages[k].parentid == bindid) ...
```

搜索范围是 `LayerArray[parentid].Barrages` —— **`Batch.parentid` 就是图层号**，
所以炮塔只认**同一图层**里那些 `Barrage.parentid == bindid` 的载体。
`Batch.parentid`（图层号）和 `Barrage.parentid`（造它的批次 id）是**同名不同义**的两个东西。

⚠ b660 三个图层**都有 id=1**。按全局 id 索引，`byid[1]` 会被 Layer3 的炮塔覆盖 →
枝条一（id=1）的 5 个炮塔（含 `tiao=9` 的两组，是「千本桜」的大头）**全部挂空**。

### ② 属性名到字段的映射有**四张不同的表**（`CSManager.cs:88-215`）

同一个中文词在不同事件组里是**不同的字段**：

| 词 | 父事件组（批次，`results`） | 子事件组（子弹，`results2`） |
|---|---|---|
| 半径 / 半径方向 | 2 / 3 | — |
| 角度 | 6（fdirection） | — |
| 速度 | 8（批次自身） | — |
| 宽比 / 高比 | 14 / 15 | 2 / 3 |
| 不透明度 | 19 | 7 |
| 朝向 | 20 | 8 |
| **子弹速度** | **21（sonspeed）** | **9（子弹自己的 speed）** |

所以「子弹速度」在批次上是「之后发出的弹多快」，在子弹上是「这颗弹自己多快」——
完全两回事。漏了子事件组，花瓣就永远是出生时那点大小。

### ③ 子事件组是**花瓣张开**的来源（这是「缩放不对」的根因）

子事件组（字段 52）改的是**每颗子弹自己**的属性，且时间轴是 `time - (Mist ? 15 : 0)`
（`Barrage.cs:475`）。b660 的炮塔全都靠它：

```
当前帧=1：宽比变化到0.8，正比，24帧      ← 花瓣 24 帧里从 0.1 张到 0.8
当前帧=1：高比变化到0.8，正比，24帧
当前帧=261：子弹速度增加0.45，正比，360帧  ← 越晚的弹越快
当前帧=1：朝向增加120，正比，140帧（事件组 t=140 add=140）← 花瓣自己转
```

id=12/13 更特别：出生 `alpha=0`，到第 **601 / 1201** 帧才「不透明度变化到100」——
是**第二、第三圈**才现身的花（`sonlife=3413` 撑得到）。

### ④ 坐标是 **1:1**，中心 (320,240)

> ⚠ **本节有错，见第十五节**：中心是 **`(315,240)`**（`Center.cs:76-77` 的默认值 `x=315f`）。
> 差 5px，整卡横向偏移一截。本节其余（1:1、384×448）是对的。

CS 逻辑窗口 640×480，场地就是正中那块 384×448；LuaSTG 的 world 也是 384×448
（`THlib/lib/Lscreen.lua:51`）。所以

```
lua_x = cs_x - 320      lua_y = 240 - cs_y      lua_angle = -cs_angle
```

验证：`fy=480` → lua_y = −240，正好是 448 场地底下再往下 16 px（窗口下边距）✓。

### ⑤ 「额外发射」不是每个批次都有

`当前帧=1：额外发射` = `special == 2` → 当场 `Shoot()`。b660 里**只有**
id=0,1,2,7,9,10,11,12,13,14 有；**id=3/4/5/6 没有**（正是竖向那几根枝条）。
给它们硬加一轮，就是「开卡多出来的散射弹」。

### ⑥ 超出 `life` 的事件是**死事件**

根批次 `life=13`，却写着「当前帧=17/18/22：半径方向增加90 / 半径增加130 / 半径减少70」。
`Deepbind=False`，没有克隆体去跑它们，本体在第 13 帧就没了 —— 编辑器里留下的死数据，
**不要照着写**。

### ⑦ 修完后的读数

b660 稳态同屏 **578 发**（修正前 284，再前一版 286）。节点位置可逐点复算验证，例如
枝条一首节点：`ax=CX(132)=−188, ay=CY(140)=100, rd=−11`，`额外发射` 在第 1 帧先发一轮
（r = 440/16 = 27.5）→ 应落在 `(−161.0, 94.8)`，实测一致。

## 十四、自检工具本身修掉的两个 bug

这两个不在关卡里，在 `tools/check_stage.lua`，但影响**所有**测量：

### ① `task.Wait(1)` 被当成等 2 帧 —— 整个自检的时间轴只有真实速度的一半

引擎里 `task.Wait(1)` 是一次裸 `cor.yield()`，也就是**下一帧**恢复
（`THlib/lib/Ltask.lua:68-77`）。桩件原来 `yield(1)` + `wait = 1`，中间白白跳一帧。
于是所有图案被拉长一倍：帧数、峰值、循环次数**全部对不上**，之前量的威胁度也一并作废。

修法：`t.wait = math.max((delay or 1) - 1, 0)`。

**连带后果**：th04 重测威胁度 0.53~1.32（仍合格），但**威胁组数掉到 0.57~0.63**，
低于文档要求的 1~2 —— 半速模拟掩盖了「卡偏稀」这个问题。

### ② 全大写的未知全局现在直接判失败

桩环境对未知全局返回 nil，所以 `_SCBG`（正确是 `_SC_BG`）这类**拼错**原来只躺在
「缺少桩件」的警告列表里，一路漏到真机才炸成 `attempt to index global 'X' (a nil value)`。
现在凡匹配 `^_?[A-Z][A-Z0-9_]*$` 的未知全局一律 FAIL。

顺带把 `_SC_BG` 的桩件补成真实现（`AddLayer` 必须返回真的图层表），
另外 16 个此前「载入中途就炸、后面的 boss 根本没注册上」的关卡文件也能载入了 ——
注册数从 186 张卡涨到 **397 张**。

## 十五、第三次修正：手抄字段被机器生成取代，以及七个运行时语义

这一轮不再靠手抄表，改用 `tools/thmhj_tolua.py` 把 `b<id>.xna` 机械翻译成
`run_cs` 的批次表。原因是上一版 24 个批次 × 40 个字段全靠手写，每改一轮就换一处错，
用户看到的现象也每轮都变。生成之后「数据 → Lua」这一步不再有出错空间，
**手写的只剩运行时语义**（这些能从 C# 一次读懂、一次写对）。

### 先纠正第十三节的四处**错**结论（错笔记比没有笔记更坏）

| ④ 坐标中心 (320,240) | **`(315,240)`**（`Center.cs:76-77` 默认 `x=315f`）。差 5px，整卡的横向位置偏一截 |

### 运行时语义（这一轮新读到的，全部有出处）

1. **子事件的状态是「每颗子弹一份」**（`Batch.cs:1690-1695`：`Shoot` 对每颗子弹
   `barrage.Events.Add(Event.Get()...)` 克隆一套事件组）。
   共用一个状态的后果极隐蔽：`ctime` 被同批次数百颗子弹每帧各扣一次，
   「持续 140 帧」的事件在十几帧内耗尽 —— 花瓣只会抖一下就不再自转。
2. **挂载树可以不止两层**：两条 `Shoot` 分支都 `barrage.parentid = id` 再入表
   （根 `Batch.cs:1695`、炮塔分支同样），炮塔扫描的是「`parentid == bindid` 的所有活子弹」。
   b660 的枝条三是**三层**（枝条 `id=14` → 二级载体 `id=3` → `id=4/5/6`）。
3. **回卷时不清在飞的子弹**：`Time.cs` 只重抄批次。所以**上一圈打出的载体，
   这一圈照样能被炮塔挂上**。b660 的 Layer3 靠这个：根 `begin=510`、炮塔 `181~300`
   第一圈永不相交，载体 `sonlife=1200` 跨过 600 帧的回卷点，从**第二圈**起才出尾迹。
4. **判定前提是 `alpha > 95`**（`Barrage.cs:1487`）。所以「不透明度」是玩法数据：
   b660 的花瓣出生 `alpha=0`（无害），第 601/1201 帧「不透明度变化到100」才变得致命。
   `Invincible` **不是**无判定 —— 它是「子弹不会被自机打掉」（`Barrage.cs:1474`）。
5. **CS 的离屏回收框比屏幕大得多**（`Barrage.cs:1586-1599`）：默认 lua
   `x∈[−631,452] y∈[−575,573]`，`Outdispel=true` 时 `x∈[−331,230] y∈[−275,273]`。
   所以子弹出屏后**还会活着飞一段**。移植里要 `bound = false` 交给这个框，
   否则尾迹的载体在第一圈就被引擎删掉。
6. **`Mist`**：前 15 帧**不画子弹本身**，画的是从 1.5× 缩下来、渐显的雾
   （`Barrage.cs:1623-1632`），且这 15 帧内子事件时间轴整体推后（`conditions[0] = time - add`）。
   判定不受影响（第 4 条看的是字段值）。
7. **`aspeed`/`aspeedd` 只在子弹出生的那一帧**算成 `aspeedx/aspeedy`
   （`Barrage.cs:396-397` 在 `time==1` 块里），之后子事件再改它**无效** —— 原版的怪癖，照做。

### 贴图朝向：实测出来的

`Tg225` 实测是 64×64 的**各向同性光斑**（二阶矩长宽比 1.0），**不是**竖直的激光贴图。
光柱的「竖」来自 `hscale 2.0 > wscale 1.2` 这种非等比缩放；缩放是在贴图本地坐标系里做的，
所以 `rot` 一转让长轴跟着转 —— `head 270/290/230` 就是让三根柱子的长轴偏
0°/20°/−40° 张成扇形。移植里 `rot = head_lua − 90`（引擎固定 `+π/2` 再按 y 翻转取负）。

### 自检工具这一轮修掉的三个 bug（都在 `tools/`）

1. `thmhj_dump.py` 的 `SHOW` 列表漏了 `head` / `Withspeedd` / `Mist` / `xscale` / `yscale` ——
   **决定贴图转不转的字段一个都没打印**，所以「贴图躺倒」这类问题根本没法核对。
2. 同一个文件把 `p[51]`（父事件组）**硬标成「父事件组」**，且从不打印 `p[52]`（子事件组）。
   结果是全部子事件不可见 —— 上面第 1 条的病根就在这里。
3. `thmhj_tolua.py` 的动词识别写成 `action.startswith(动词)`，而实际是
   `速度增加3` 这种「属性名在前、动词在中间」，要 `find` 后切两半。
